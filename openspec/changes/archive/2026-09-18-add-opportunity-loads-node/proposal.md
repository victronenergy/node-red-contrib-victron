## Why

node-red-contrib-victron already exposes every major Victron device type (battery, solarcharger, settings, ...) as generic read/write nodes, but has no coverage for Opportunity Loads - the reactive surplus-solar-consumption engine (`venus-opportunity-loads`, D-Bus service `com.victronenergy.opportunityloads`) that Victron positions as a more capable alternative to scheduling solar surplus than Dynamic ESS. Flow builders currently have no way to see what it's doing (allocation state, per-load status) or adjust its behaviour (priorities, reservation curve, enable/disable) from Node-RED. This change closes that gap, and is deliberately scoped to prove out the cheapest possible way to add a new device type to this project - a template for future additions.

## What Changes

- Add a new `opportunityloads` device type entry to `src/services/services.json`, spanning two D-Bus services under one node (the same multi-service-per-device-type pattern the existing `dess` device type already uses for `settings`+`system`):
  - `com.victronenergy.opportunityloads`: read-only `/OperationalState`, `/BatteryReservation`, `/BatteryReservationState`; read/write `/ReservationStartSoc`, `/ReservationBasePower`, `/ReservationEndPower`, `/NominalInverterUtilizationLimit`, `/BalancingThreshold`, `/PauseWhenOffgrid`, `/BatteryLifeSupport`, `/DisableEvcsControl`; and the load priority list `/AvailableServices` as a plain `string`-typed path (mode `both`) - a flow reads the current JSON array and can write back a reordered one, no bespoke drag/reorder widget.
  - `com.victronenergy.platform`: read/write `/Services/OpportunityLoads/Mode` (the enable/disable switch), which lives on this separate platform-wide service rather than on `opportunityloads` itself.
  - Per-load live allocation (`/Consumers/<id>/*`) and a handful of internal/advanced settings (`ControlLoopInterval`, `DisableEvcsQuirks`, `EnableDebugLogging`, `BatteryReservationEquation`, `PriorityMapping`) are deliberately excluded from v1 - see Impact and `design.md`.
- No new node *behavior* is written: this relies entirely on the existing generic `BaseInputNode`/`BaseOutputNode` machinery in `victron-nodes.js`/`victron-nodes.html` and the service-lookup logic in `victron-system.js`, exactly the way every other device type (e.g. `settings`, `battery`) already works. There is a small amount of mechanical, one-line-per-type registration still required, matching every existing device type, in four places: a server-side `RED.nodes.registerType(...)` call pair in `victron-nodes.js`, a client-side `registerInputNode`/`registerOutputNode` call pair in `victron-nodes.html`, a `listAvailableServices()` entry pair in `victron-system.js`, and a label entry in `service-meta.json`. No new logic, HTML structure, or CSS - just the same boilerplate every other device type already has (confirmed by starting Node-RED and checking the palette - the server-side registration was initially missed and the node type didn't appear until it was added).
- **Design guide compliance** (per `docs/NODE_EDIT_DIALOG_DESIGN_GUIDE.md`): no new edit-dialog HTML/CSS is authored, so the guide's CSS-isolation, required-resources, and standard-HTML-structure sections are satisfied automatically by reusing the existing generic template (the same one every other device type already renders through). The only user-facing addition is a handful of new fields inside that existing template (label + tooltip per path, generated the same way `battery`/`settings` paths already are) - no new field types, icons, or message-box patterns are introduced, so no deviation from the guide is needed.

## Capabilities

### New Capabilities
- `opportunity-loads`: monitoring and configuring Victron's Opportunity Loads feature (`com.victronenergy.opportunityloads`) from Node-RED flows via read/write D-Bus paths, using the project's existing generic input/output node pattern.

### Modified Capabilities
- None. This project has no previously-specced capabilities to modify (its `openspec/specs/` directory is currently empty); this change introduces the first one.

## Impact

- **Code**: `src/services/services.json` only (new `opportunityloads` key). No changes needed to `victron-nodes.js`, `victron-nodes.html`, `victron-system.js`, or `dbus-listener.js` for the scalar paths.
- **Resolved during design**: `/Consumers/<id>/*` (per-load live allocation) is excluded from this change. These paths are gated behind `venus-opportunity-loads`'s own `EnableDebugLogging` setting and don't exist on D-Bus during normal operation (confirmed in its source) - not something this project's wildcard expansion can work around. Per-load visibility in v1 is limited to identity and priority order via `/AvailableServices`; see `design.md` for details.
- **External dependency**: `venus-opportunity-loads` is pre-1.0/beta (its own priority-mapping/`AvailableServices` write path is flagged by its maintainers as needing a rewrite). This node's write paths inherit that instability - worth flagging to users in the node's help text rather than blocking the change on it.
- **Node-RED palette**: adds "Opportunity Loads" and "Opportunity Loads Control" under the existing "Victron Energy" category. No changes to any other existing node.
- **Documentation**: `README.md`/node help text needs a short section, following the existing per-device-type pattern (see `services.json`'s `help.both`/`help.input`/`help.output` fields).
- **Deferred concern (not addressed by this change)**: this change follows the project's current one-node-type-per-device-type pattern, adding two more entries ("Opportunity Loads" / "Opportunity Loads Control") to an already large Node-RED palette. That pattern itself is not something the maintainer is happy to keep extending indefinitely - a future redesign toward fewer, more theme-based nodes (e.g. grouping related device types rather than one node per type, and not collapsing to a single universal node) is wanted, with any such redesign required to keep existing flows working (migratable, not breaking). This change intentionally does not attempt that redesign; it's flagged here so the tradeoff is visible rather than silently repeated.
